\section{Product vision and user journey}

EnergyAI turns the validated forecasting workflow into an application that a non-research user can operate without choosing neural architectures or manipulating notebooks. The primary journey is deliberately short: authenticate, configure a site and meter, import energy history or start the labelled demonstration simulator, inspect data quality, select 24 hours, 168 hours, or 30 days, generate a forecast, and review the result with its uncertainty, cadence, and provenance. Model selection is a backend responsibility governed by the artifact registry.

The platform does not expose every research feature. Product V1 prioritizes Dashboard, Usage, Forecast, Actions, and Settings. Administrative views are role-gated. Simulation is a secondary, explicitly synthetic demonstration surface; research model selection remains a backend and evidence-registry concern rather than a normal-user control.

The presentation layer uses Next.js 16, React 19, TypeScript, Tailwind CSS, and reusable UI components. The API layer uses FastAPI and Pydantic schemas. Persistence uses SQLAlchemy models, Alembic migrations, and PostgreSQL 16. Separate worker services handle alert, email, and avatar-cleanup responsibilities. The model layer contains fixed Global TFT artifacts plus the checksum-addressed Chronos-2 month adapter and pinned base revision.

The Docker Compose configuration defines six services: PostgreSQL, backend, frontend, alert worker, email worker, and avatar-cleanup worker. At the verified local checkpoint, database, backend, and frontend health checks pass and the three workers run. The public Azure topology deploys the web, API, and email-worker containers, with PostgreSQL provided as a managed service. Alert and avatar-cleanup workers remain local-only. This distinction prevents local worker readiness from being misreported as cloud worker availability.

\section{Frontend design}

The Next.js application provides authenticated and public routes. Public routes include the landing page, registration and login, password recovery, email verification states, privacy, terms, and support. The normal-user navigation contains exactly five primary destinations: \texttt{/dashboard}, \texttt{/usage}, \texttt{/forecast}, \texttt{/actions}, and \texttt{/settings}. Compatibility routes redirect \texttt{/consumption} to Usage; \texttt{/alerts} and \texttt{/recommendations} to Actions; and \texttt{/reports} to Usage. The \texttt{/admin} view is rendered only for an administrator.

The interface uses explicit empty, loading, blocked, error, and success states. This is particularly important for forecasting. A missing model, insufficient history, disabled capability, or failed data-quality gate must be explained rather than replaced by a synthetic chart. Horizon state is persisted across 24-hour, 168-hour, and 30-day views. Daily labels, cards, chart axes, peak descriptions, and PDF names are derived from the returned cadence instead of dividing an assumed hourly series. The demonstration-history shortcut is intentionally unavailable for the month model because its 30-day bootstrap cannot satisfy the 270-day readiness gate.

\section{Backend API and domain model}

FastAPI routers separate authentication, account lifecycle, settings, ingestion, consumption, forecasting, analytics, alerts, recommendations, simulation, monitoring, system health, and administration. Importing the current application and generating its OpenAPI schema yields exactly 80 method--path operations across 74 unique paths, including the two root health operations. Pydantic request and response models define validation boundaries, while dependency functions enforce authentication, role, and ownership rules.

The core domain model is shown in \cref{fig:classdomain}. A User owns one or more Sites; a Site contains Meters; meter observations are stored as SmartMeterReading records; IngestionBatch records summarize import operations; Forecast records preserve output and horizon provenance; AlertConfig and Alert represent policy and detected conditions; Recommendations record suggested actions. Additional entities support refresh tokens, account-action tokens, OAuth challenges, outbox delivery, audit events, budgets, and system settings.

\section{Authentication, JWT sessions, and RBAC}

Local login verifies a bcrypt password hash. On success, the backend returns an access token and sets refresh state through an HttpOnly cookie. The server stores refresh-token hashes and supports rotation, logout, and logout-all operations. This design reduces exposure compared with storing long-lived refresh credentials in browser local storage.

\ac{rbac} protects administrative operations. Ownership checks are also required for normal-user resources: role membership alone must not permit access to another user's site, readings, forecast history, or alerts. Account actions cover email verification, password reset, Google identity linking where configured, data export, avatar management, and irreversible deletion with recent-authentication controls. Permanent deletion performs explicit ordered, set-based deletes across audit history, outbox state, OAuth challenges, recommendations, alerts, forecasts, budgets, readings, ingestion batches, meters, simulator sessions, sites, tokens, linked identities, and the user. This avoids loading thousands of readings and invoking an unbounded ORM cascade inside one request. The transaction preserves only a new anonymized \texttt{account.deleted} audit event after the ownership graph is removed.

\section{CSV ingestion and validation}

The product input contract is intentionally simple: timestamps and energy values in kWh. A meter-scoped preview endpoint parses a bounded sample and returns detected columns and validation information. Import is a separate confirmed operation. The backend verifies ownership, normalizes supported timestamps, rejects invalid rows, bounds file/row processing, stores accepted readings transactionally, and records an ingestion batch.

This separation improves safety and usability. A user can identify a wrong delimiter, timestamp column, or unit before modifying persisted history. Duplicate or malformed timestamps are not silently converted into model-ready data. CSV preview remains available while the simulator runs. At confirmed import time, the client refreshes simulator status and warns that continuing the live synthetic feed could mix sources. Consent stops the simulator before import; cancellation writes nothing. Historical simulation rows remain labelled and are not automatically deleted. The simulator page provides a matching ``Stop demo and use real data'' action that links directly to the importer. The consumption API supports period summaries, paginated readings, current/history statistics, and export.

\section{Persistent deterministic demonstration history}

The demonstration simulator is persistent and source-aware. On its first start for an empty primary meter, it creates 30 days of household history at 15-minute intervals, or 2,881 timestamped readings including both boundary points. Each value is a deterministic function of a site-specific seed, timestamp, and profile version. The profile combines an overnight base load, morning and evening peaks, weekday and weekend differences, and bounded variation. Electrical companion values remain deterministic and physically consistent. Every generated row uses \texttt{source="simulation"} and simulated quality metadata, so no synthetic point is presented as measured electricity.

Azure may scale the API to zero while the simulator session remains logically running. On the next backend start, catch-up advances only from the latest eligible simulation reading and never searches for arbitrary historical holes. A continuity marker prevents the feature from rewriting gaps that existed before deployment; stopping and later restarting the simulator establishes a new boundary so the stopped interval also remains visible. Ordinary catch-up retains the 15-minute cadence. Exceptionally long outages select progressively coarser intervals and never exceed 5,000 generated points. The unique meter/timestamp constraint and deterministic ingestion keys make bootstrap and catch-up idempotent under replay.

The explicit ``Reset demo data'' operation deletes and regenerates only simulator-owned readings and batches. CSV and push readings remain unchanged, login never generates history, and a non-empty imported or measured meter is not automatically bootstrapped. This boundary provides at least 720 hours of reproducible demonstration context while preserving the data-integrity story of real acquisition paths.

\section{Forecasting service and artifact contracts}

The forecast router exposes capabilities, readiness, demo-history preparation, run, latest, and history operations. For 24 and 168 hours, the service validates and normalizes the latest 336-hour window before TFT inference. For the month capability, it integrates persisted meter intervals into rolling 24-hour energy blocks, requires at least 270 complete daily values within a maximum 365-day context, performs causal interpolation only across bounded internal missing days, and invokes the checksum-verified Chronos-2 LoRA release. Forecast records preserve target count, interval length, resolution, input range, and model provenance so that retrieval and PDF generation cannot reinterpret 30 daily targets as 720 hourly points.

\section{Dashboard, actions, alerts, and reports}

The dashboard aggregates current consumption, historical trend, forecast summary, and prioritized actions from database-backed APIs. Its ``At a glance'' narrative explains the selected period before requiring a user to decode the cards: how much energy and estimated cost were observed, when the peak occurred, how the period compares, whether data are fresh and sufficiently covered, which sources contributed, and what action is most relevant. Simulation provenance receives a prominent trust message whenever synthetic readings contribute. The Usage area focuses on measurements and export. Forecast focuses on horizon selection, readiness, quantiles, validation context, and history. Actions combine recommendations and alert state so that the prediction can lead to a practical response rather than remain an isolated chart.

Alerts have acknowledged, resolved, and reopened states and a per-user configuration. Background workers support alert generation and delivery responsibilities. Recommendations can also be updated through explicit status transitions. PDF export is available from the forecasting workflow through the analytics endpoint. The legacy \texttt{/reports} page redirects to Usage; there is no separate reports workspace or external reporting warehouse.

\section{Real-time behavior and background work}

The repository contains WebSocket connection management and real-time alert behavior, along with workers for alerts, email outbox delivery, avatar cleanup, and simulator continuity. Their responsibilities are separated from ordinary user reads. Simulator history is created only by explicit simulator lifecycle operations or the startup catch-up of a session that remained running; login and dashboard requests do not write readings. The Azure deployment runs the email worker with the existing SMTP configuration, and the API reports email delivery ready. The live Google Web client also opens the account chooser for the authorized Azure origin. Provider availability remains operationally dependent, while alert and avatar-cleanup workers are not deployed in Azure.

\section{Observability and error handling}

System endpoints expose liveness, readiness, health, version, and legal information. Administrative endpoints expose user, system, and model-readiness views. Structured logging and audit events preserve significant account, authentication, ingestion, and forecast actions. User-facing errors use explicit codes and messages rather than leaking internal exception details.

The product must distinguish service readiness from model readiness. A healthy FastAPI process can still lack a valid forecasting artifact or sufficient site history. Conversely, a valid artifact does not make external email or OAuth providers ready. Separate capability responses allow the frontend to present these states accurately.

\section{UI/UX and accessibility considerations}

The interface uses a consistent dark visual language, responsive layouts, labeled controls, status messages, concise narrative interpretation, and chart alternatives where practical. Browser tests cover desktop Chromium, Firefox, WebKit, and 360, 390, and 768-pixel responsive projects. Accessibility is not claimed as certified: a formal WCAG audit, keyboard-only review, screen-reader validation, and contrast inventory remain future work.

\section{Local Docker deployment}

The verified local deployment profile is reproducible:
\begin{lstlisting}[language=bash]
docker compose up --build -d
docker compose ps
curl http://localhost:8000/api/v1/system/live
curl http://localhost:8000/api/v1/system/ready
\end{lstlisting}
Environment configuration must replace insecure sentinel secrets before startup. PostgreSQL data and avatars use named volumes. Alembic migrations run against the configured database. Model artifacts are packaged in the backend image or mounted according to the repository's Compose build context. The production build includes the exact month adapter and cached base model; deployments may disable the month capability explicitly but do not download mutable weights at request time.

The original jury-release smoke test returned HTTP 200 for the frontend, Login, Register, Privacy, and Terms pages and \texttt{ready=true} for the API. That evidence predates the repository month integration; an Azure promotion of the new foundation-model image is not claimed in this report.

This is a controlled public PFE deployment rather than a claim of complete production maturity. The deployment uses Azure-generated hostnames rather than a custom domain. Public email registration, verification delivery, the email worker, and Google identity are enabled, but no sustained provider/load test is claimed. Alert and avatar-cleanup workers from Compose are not deployed, uploaded avatars are not durably persisted, centralized Log Analytics retention is disabled, the registry uses deployment credentials rather than workload identity, and no backup restoration, load, disaster-recovery, formal accessibility, or penetration test has been completed. The PostgreSQL firewall accepts Azure-originated services but no temporary developer-IP rule remains. The monthly budget sends notifications but is not an automatic application shutdown policy. Older revisions remain inactive; rollback selection must preserve compatible web and API versions.

\section{Implementation summary}

EnergyAI's engineering contribution is an inspectable boundary between scientific artifacts and product behavior. The application exposes only supported capabilities, distinguishes hourly and daily cadence, verifies artifact identity, rejects insufficient input, records provenance, isolates user data, preserves uncertainty, labels every synthetic reading, and keeps simulator continuity separate from measured-data gaps. The active release deliberately keeps the compact TFTs for day/week and uses Chronos-2 only where it fills the missing month capability. The next chapter evaluates the quality evidence for this implementation and states what remains conditional.
