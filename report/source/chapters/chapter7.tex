\section{Validation scope and evidence date}

The software-validation evidence in this chapter begins with the full application audit performed on 31 July 2026 and ends with the post-release CI and Azure revision checks on 9 August 2026. Historical reports are retained for chronology because test counts, routes, and capabilities changed over time. The audit used both SQLite and a disposable PostgreSQL database, frontend quality commands, a six-project browser matrix, dependency audits, artifact checks, Docker health, and source review. The checkpoint quantile reanalysis and the separate serving-normalization evaluation were generated on 1 August 2026; each is identified by script, input, checkpoint, environment, and output hashes. The latest coordinated validation targeted commit \texttt{6796b1ec7360f9c05cb804fbd8be29ba1ea78ef8}; it did not rerun or alter any scientific experiment.

\section{Backend validation}

The current local backend suite passed 112 tests with four expected PostgreSQL-only skips under SQLite. The additional cases cover deterministic simulator history, continuity and reset behavior, plus permanent deletion after a full 2,881-point simulator bootstrap. A focused local PostgreSQL deletion test removed the resulting ownership graph in 0.272 seconds. In the earlier full audit, a uniquely named disposable PostgreSQL database was created on the running server, migrated from an empty schema through all 17 Alembic revisions, tested, and removed in cleanup. That historical result remains 100 passed and zero skipped in 42.78 seconds, with one warning. The current CI also migrated an empty PostgreSQL service, passed the backend suite, audited dependencies, built the backend test image, and passed the suite again inside that image. No schema migration was required for the simulator continuity, CSV handoff, or deletion changes.

The PostgreSQL run is the stronger result because it exercises locking and database behavior that SQLite cannot reproduce. It also confirms that migrations can construct the schema from empty state. The audit did not mutate the live product database.

No coverage percentage is claimed. Test count and coverage are different measures; passing suites do not prove that every path is exercised.

\section{Model-contract and artifact validation}

The product does not rely only on a database model name. Artifact tests verify manifest parsing, supported horizon, checksum, strict state-dict load, CPU inference, finite output, expected shape, and reference points where recorded. Both 24-hour and 168-hour capabilities are packaged. The checkpoints share a file size of 5,600,105 bytes but have distinct SHA-256 hashes, confirming that the weekly artifact is not merely a renamed daily file.

The manifests also preserve limitations. London-cohort metrics are not a guarantee for a client site. New sites use their recent 336-hour window for normalization, while the frozen research metrics use each evaluation household's pre-validation training-segment statistics. The supplementary inference-only evaluation now measures this transform change on the same frozen London cohort and reports it separately from the research headlines. Quantile outputs have not been recalibrated per site. Week-ahead uncertainty grows with the horizon and must be displayed with provenance.

\section{Security validation}

The audit reviewed password hashing, JWT and refresh-token behavior, account-action tokens, Google identity gating, role checks, ownership filters, upload bounds, request validation, SSRF controls, and secret configuration. CI includes a full-history gitleaks job. No P0 authentication bypass or data-loss defect was identified. Permanent account deletion is additionally protected by recent password reauthentication and a literal confirmation value. Its implementation removes the complete ownership graph with ordered set-based statements, then writes only an anonymized deletion audit event, avoiding the request timeout observed with the earlier row-by-row ORM cascade.

One current security-quality concern remains: the frontend application does not define its own complete security-header policy such as CSP, frame policy, content-type options, or referrer policy. Azure supplies managed HTTPS ingress, but transport security does not by itself establish a complete application-header policy. After dependency overrides and lockfile normalization, the final npm audit and the production Python requirements audit reported zero known vulnerabilities. Google integration uses only the public client ID; no provider secret is required or stored by EnergyAI.

\section{Docker and deployed service health}

After Docker Desktop was started, the six-service Compose stack built and ran. PostgreSQL, backend, and frontend reported healthy; alert, email, and avatar-cleanup workers remained running. Health endpoints returned successful responses and both forecasting artifacts were available.

The final Azure smoke test confirmed public TLS and HTTP 200 for the principal public pages, API liveness and readiness, managed-database connectivity, warmed 24-hour and 168-hour models, ready SMTP capability, and a healthy one-replica email worker. Google identity is published for external users, and the live account chooser opened for the exact Azure origin without creating a test user. A subsequent read-only Azure check found \texttt{ca-energyai-web--v1-f807316}, \texttt{ca-energyai-api--v1-6796b1e}, and \texttt{ca-energyai-email-worker--v1-6796b1e} active and healthy, with 100\% traffic on the new web and API revisions. The web and API retain zero-to-one scaling; the email worker remains at one replica. Operational readiness is therefore demonstrated for a controlled public PFE presentation, while production hardening remains conditional on security headers, durable avatar storage, centralized monitoring, Azure alert/avatar workers, restore evidence, load testing, and disaster-recovery procedures.

\section{Requirement-to-test traceability}

The report's traceability registry maps each major requirement to code and validation evidence. Examples include JWT authentication to authentication tests, RBAC to admin authorization tests, per-user data isolation to PostgreSQL integration tests, CSV preview/import and simulator handoff to ingestion/browser tests, persistent demonstration continuity to simulator tests, bounded account deletion to ownership-graph tests, and each forecast horizon to model-contract and dual-horizon browser tests. The complete machine-readable matrix is stored in \evidence{report/evidence/requirements\_traceability.csv}.

Traceability does not remove the need for judgment. For example, a route and test can show that account deletion works, but legal compliance requires institutional and jurisdiction-specific review. Likewise, an artifact test proves file identity and output shape, not real-world forecast calibration.

\section{Scientific limitations}

\subsection{Geographic transfer}

The final model evidence comes from Low Carbon London. Climate, building characteristics, tariffs, appliance ownership, and daily routines can differ materially in Morocco. Cold-start evaluation within London is stronger than random household windows, but it is not cross-country validation. A Moroccan pilot cohort is required before making local performance guarantees.

\subsection{Input scope}

The product contract uses timestamp and energy. This lowers onboarding friction but excludes weather, occupancy, tariff events, and building metadata that may explain regime changes. Calendar features are deterministic, not measurements. Future work should compare the marginal value of weather forecasts and static site attributes under a strictly causal protocol.

\subsection{Uncertainty calibration}

The TFT produces 0.1, 0.5, and 0.9 quantiles, but the manifests state that they are not recalibrated for each client. Reanalysis under the original research scaler finds 80.7963\% empirical coverage for the nominal central 80\% interval at 24 hours and 78.3518\% at 168 hours, with mean widths of 0.559770 and 0.585659 kWh. Under serving normalization, coverage is 81.0108\% and 78.0556\%, with widths of 0.571945 and 0.598749 kWh. This closes the scaler-specific comparison on the frozen London cohort, but not site-level calibration. Conformal time-series methods are a candidate extension if their assumptions, calibration cohort, and deployment contract are stated explicitly \cite{stankeviciute2021conformal}.

\subsection{Research-to-serving preprocessing}

The cold-start experiment gives every held-out London household a mean and standard deviation fitted on its own historical training segment; the application instead estimates both statistics from the current 336-hour request window. The preserved artifacts were sufficient to rerun exactly the same cold households, fixed origins, histories, targets, seasonal baselines, calendar features, and checkpoints with the production rolling normalization and output transform. Macro MAE is 0.181945 kWh at 24 hours and 0.194138 kWh at 168 hours under that serving transform, compared with the unchanged research headlines of 0.184928 and 0.197322 kWh. This resolves the identified transform mismatch for the frozen LCL cohort. It does not establish expected accuracy for an arbitrary new site because geography, data quality, time-zone handling, and calibration may differ.

\subsection{Monthly horizon}

Monthly candidates beat the seasonal baseline in average MAE by 5-8\%, but their cold-start macro $R^2$ values are negative. This conflict demonstrates why a single favorable metric is insufficient. Monthly forecasting remains experimental until household-level consistency improves.

\subsection{Experiment completeness}

TimePro and TimeMixer++ were attempted but lack completed leaderboard evidence. TSMixer appears in an exploratory weather notebook without a frozen successful metric artifact. MultiCycleNet was adapted locally and requires final primary-reference verification before any claim of exact reproduction. These gaps are reported rather than filled with inferred results.

\section{Product limitations}

The release has verified public web and API URLs, email registration and delivery capability, a healthy email worker, and a production Google identity origin, but that does not make every repository capability operational in the cloud. Alert and avatar-cleanup workers are absent; avatars are ephemeral; centralized log retention is not configured; and backup restoration has not been tested. The Azure-generated hostname is not a custom domain, the registry is not yet integrated through workload identity, and the budget is an alerting control rather than an automatic shutdown. Application security headers still require review. Formal accessibility, load, disaster-recovery, sustained provider, and multi-tenant penetration testing remain incomplete. The research tree also contains historical assets that should remain separated from the deployable product snapshot.

\section{Discussion}

The project demonstrates a change in what counts as success. At the beginning, success meant matching a 98\% article result. After the audit, success meant constructing a task that could fail honestly. That shift led to lower and more interpretable metrics, stronger baselines, broader household analysis, and explicit artifact limitations.

The final TFT research results are credible because they satisfy several independent conditions: the target is continuous and future-indexed; all households share one causal chronology; households are evaluated in a cold-start cohort; the model beats a seasonal baseline for nearly all evaluated households; median, p90, bias, and interval diagnostics are reported; and the original checkpoints are hash-identified. The application adds strict loading and refuses unsupported horizons. The separate serving-normalization evaluation extends this evidence to the rolling transform on the same frozen cohort. These facts support a controlled demonstration and a defensible PFE contribution, but they do not establish geographic transfer or site-specific calibration.

The remaining conditional findings also improve rather than weaken the report. They separate verified public availability from full production maturity and prevent a controlled academic deployment from being misrepresented as a globally validated service.
